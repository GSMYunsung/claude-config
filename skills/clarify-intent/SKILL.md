# 의도 확정 (clarify-intent)

사용자의 말은 해결책의 형태로 들어오는 경우가 많다("여기 고쳐줘", "이걸로 바꿔줘").
이 스킬의 목적은 그 말 뒤에 있는 **진짜 목표**를 확정한 뒤에 해법을 고르는 것이다.

확정한 의도는 채팅에만 두지 않고 **GitHub 이슈**로 남긴다. 코드만으로는 "왜 시작했고 무엇을 하기로 했는지"가 남지 않기 때문이다.
맥락을 위한 별도 MD 문서는 만들지 않는다. 이슈는 맥락과 진행 기록, PR은 결과 보고서 역할을 한다. (`pr-workflow` 스킬)
`CLAUDE.md`는 예외가 아니라 역할이 다르다. 작업과 관계없이 **바뀌지 않는 제품 기준**(상위 목표, 완성도 축, 우선순위)만 두고, 작업별 맥락이나 진행 상황은 넣지 않는다.

## 가장 중요한 규칙: 이해 보고 → 확정 → 이슈 → 착수

**작업에 착수하기 전에 반드시 이해한 내용을 사용자에게 보고하고, 사용자와 확정한 다음에 시작한다.** 규모와 관계없이 지킨다.

1. **보고**: 네 단계를 거쳐 이해한 내용을 아래 "의도 확정 브리프"로 보여 준다. 내가 이해한 것과 추측한 것을 구분해서 쓴다.
2. **확정**: 브리프 끝에 "이대로 진행할까요?"를 묻고 응답을 기다린다. 그 턴은 거기서 끝낸다.
3. **수정**: 사용자가 고치거나 보탠 내용이 있으면 브리프를 갱신해서 다시 보여 주고 다시 확정을 받는다. 바뀐 부분을 표시한다.
4. **이슈**: 사용자가 분명히 동의하면 ("좋아", "진행해", "그렇게 해", "추천대로" 등) 확정한 브리프를 `pr-workflow` 스킬로 **GitHub 이슈로 만든다.** 이후 작업의 기준은 채팅이 아니라 이 이슈다.
   - 다른 질문을 하거나 일부만 답한 것은 확정이 아니다.
   - 사용자의 답으로 정해진 내용(질문에 대한 선택)은 브리프에 반영한 뒤 이슈로 만든다. "확인이 필요한 것"이 남은 채로 이슈를 만들지 않는다.
5. **착수**: 이슈를 만든 뒤 `pr-workflow`의 절차대로 브랜치를 만들고 작업한다.
   - 이슈의 "작업 범위"만 작업한다. 작업 중 범위 밖의 문제를 발견하면 고치지 말고 사용자에게 보고하고, 확정되면 이슈에 댓글로 범위 변경을 남긴다. 별개 문제라면 새 이슈를 제안한다.
   - 작업 중 브리프의 전제가 틀렸다고 밝혀지면 멈추고 보고한다. 다시 확정한 내용은 이슈에 댓글로 남긴다.

확정 전에 해도 되는 것: 파일 읽기, 검색, 기존 이슈·PR 조회, 재현을 위한 실행(브라우저, curl, 테스트), 외부 조사.
확정 전에 하면 안 되는 것: 코드·문서·설정 수정, 의존성 설치, 커밋, 이슈·PR 생성.

## 규모 정하기

조사와 브리프의 깊이는 요청 규모에 맞춘다. 단, **어떤 규모든 이해 보고와 확정은 생략하지 않는다.**

| 규모 | 예 | 진행 |
| --- | --- | --- |
| 작음 | 문구 하나, 스타일 조정, 원인이 분명한 버그 | 1·2단계를 가볍게 확인하고, 짧은 브리프로 보고한 뒤 확정을 받는다 |
| 보통 | 화면 동작 변경, 규칙 하나 추가 | 네 단계 모두. 외부 조사는 필요할 때만 |
| 큼 | 새 기능, 구조 변경, 라이브러리 도입 | 네 단계 모두. 외부 조사 필수 |

## 1단계 — 의도와 배경 이해

**먼저 스스로 찾아보고, 그다음에 묻는다.**

1. 요청을 "무엇을(what)"과 "왜(why)"로 나눈다. 왜가 빠져 있으면 빈칸으로 표시해 둔다.
2. 사용자에게 묻기 전에 아래를 먼저 확인한다.
   - 관련 코드: 요청과 관련된 파일, 그 파일을 부르는 곳, 테스트
   - 문서: README, 주석, 명세
   - 이미 해결된 흔적: 같은 문제를 다루는 함수, 설정, 기존 처리
   - 지난 이슈·PR: 같은 주제를 다룬 적이 있는지 (`gh issue list --state all --search "키워드"`, `gh pr list --state all --search "키워드"`). 이전에 정한 의도나 택하지 않은 해법이 남아 있을 수 있다.
3. 코드나 문서만으로 해결되는 경우(이미 있는 기능, 설정 하나로 되는 일, 이미 정해 둔 가정)에는 그 사실을 먼저 알린다.
4. 그래도 남은 질문만 사용자에게 묻는다.
   - 코드나 문서로 답할 수 있는 것은 묻지 않는다.
   - 한 번에 모아서 묻는다. (최대 4개)
   - 각 질문에는 선택지와 추천안을 함께 준다. 열린 질문보다 고르기 쉬운 질문이 낫다.
   - 답에 따라 다음 행동이 달라지는 질문만 남긴다.

## 2단계 — 이상적인 결과, 현재 상태, 그 차이의 원인

1. **이상적인 상태**: 이 일이 끝났을 때 사용자가 보게 될 결과를 한두 문장으로 쓴다.
2. **현재 상태**: 실제로 확인한 사실만 쓴다. 재현할 수 있으면 재현한다(브라우저, curl, 테스트). 추측은 추측이라고 적는다.
3. **차이의 원인**: 왜 지금 이상적인 상태가 아닌지를 원인 단위로 쓴다. 증상과 원인을 구분한다.
4. **상위 목표 확인**: "이 요청이 해결하려는 문제는 무엇인가?"를 한 단계 더 물어 상위 목표를 적는다.
   - 상위 목표를 `CLAUDE.md`의 기준까지 이어 본다. 어디에도 닿지 않으면 그 사실을 브리프에 적고, 그래도 할지 사용자에게 묻는다.
   - 같은 목표와 관련된 열린 이슈가 있으면 함께 알린다.
5. **사용자 제안 평가**: 사용자가 방법을 제안했다면 다음을 정직하게 판단한다.
   - 그 방법이 원인을 해결하는가, 증상만 가리는가
   - 더 단순하거나 근본적인 방법이 있는가
   - 제안이 맞으면 맞다고 하고, 다르게 봐야 하면 근거와 함께 말한다.

## 3단계 — 제약과 이미 가진 자원, 외부 근거

1. **제약**: 지켜야 하는 것을 적는다. 명세, API 응답 형식, 기존 가정, 성능, 의존성 정책 등이다.
2. **이미 가진 자원**: 새로 만들기 전에 재사용할 수 있는 것을 찾는다.
   - 코드: 기존 함수, 훅, 컴포넌트, 유틸, 테스트 헬퍼
   - 도구: 이미 설치된 라이브러리의 기능, 개발 도구, 스크립트
3. **외부 근거**(보통 이상 규모에서 필요할 때): 공식 문서, 라이브러리 이슈, 널리 쓰이는 구현 사례를 찾는다.
   - 출처와 날짜를 남긴다.
4. **프로젝트에 맞는지 판단**: 외부 근거가 곧 정답은 아니다. 그 사례의 전제가 이 프로젝트와 같은지, 기존 구조와 충돌하지 않는지 따져 본다. 맞지 않으면 "참고했지만 택하지 않은 이유"를 적는다.

## 4단계 — 목표와 해법 결정

1. **무엇을 바꿀지와 어떻게 바꿀지를 나눈다.**
2. **해법 후보**는 보통 2~3개를 비교하고 하나를 추천한다. 선택지를 늘어놓기만 하지 않는다.
3. **부작용과 장애물**을 적는다.
4. **검증 계획**: 이 해법이 실제로 문제를 해결하는지 무엇으로 확인할지 적는다. 실제 검증은 구현 후 `verify-solution` 스킬로 한다.
5. **이후 비용**: 유지보수성, 새로 생기는 복잡도, 의존성, 위험을 적는다.

## 산출물: 의도 확정 브리프

네 단계를 마치면 아래 형식으로 이해한 내용을 보고하고, **확정을 받은 뒤에** 이슈로 만들고 착수한다.

```markdown
## 의도 확정 브리프

**요청**: (사용자가 한 말 그대로 한 줄)
**상위 목표**: (이 일이 결국 해결하려는 것)

**현재 상태**: (확인한 사실, 재현 결과)
**이상적인 상태**: (끝났을 때 보이는 결과)
**원인**: (증상이 아닌 원인)

**이미 있는 것**: (재사용할 코드·도구·문서)
**제약**: (지켜야 하는 것)
**외부 근거**: (출처와 함께, 프로젝트에 맞는지에 대한 판단)

**제안한 방법에 대한 판단**: (사용자가 방법을 제안했을 때만)
**추천 해법**: (무엇을 바꾸는지 / 어떻게 바꾸는지)
**다른 후보**: (택하지 않은 이유와 함께)
**부작용·장애물**:
**검증 계획**:
**이후 비용·위험**:

**확인이 필요한 것**: (남은 질문. 없으면 "없음")

**작업 범위**: (확정되면 할 일 / 이번에 하지 않을 일)

---
이렇게 이해했습니다. 이대로 진행할까요? 고칠 부분이 있으면 알려 주세요.
```

- 확인하지 못하고 추측한 내용은 `(추측)`으로 표시한다. 이슈로 옮길 때는 확정으로 사실이 된 것만 표시를 지운다.
- 작은 규모에서는 요청, 상위 목표, 원인, 추천 해법, 작업 범위, 확인이 필요한 것만 남긴다.

## 하지 말 것

- 요청을 듣자마자 해결책을 정하고 코드부터 고치기
- 코드나 문서를 보면 알 수 있는 것을 사용자에게 묻기
- 증상을 가리는 수정을 원인 해결처럼 보고하기
- 외부 사례를 맞는지 따져 보지 않고 그대로 들여오기
- 질문을 여러 번에 나눠 하나씩 묻기
- 이해 보고 없이, 또는 확정 전에 작업을 시작하기
- 확정한 범위 밖의 것을 함께 고치기
- 확정한 의도를 채팅에만 두거나, 맥락 정리용 MD 파일을 따로 만들기 (이슈에 남긴다)
