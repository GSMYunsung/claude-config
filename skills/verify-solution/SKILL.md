# 해법 검증 (verify-solution)

목표는 "테스트가 통과했다"가 아니라 **"이 변경이 원래 문제를 해결했고, 다른 것을 망가뜨리지 않았다"는 확신**이다.
확신은 실제 사용과 닮은 테스트일수록 커진다. 다만 그만큼 비용도 크므로, 변경이 일어난 위치에 맞는 층을 고른다.

## 테스트 층 (Testing Trophy)

정적 검사 → 단위 → 통합 → E2E 순서로 무게중심을 둔다.

| 층 | 역할 | 무엇을 잡나 |
| --- | --- | --- |
| 정적 검사 | 타입 검사, 린트 | 타입 불일치, 잘못된 호출 |
| 단위 | 순수 함수·유틸의 경계값 | 상태 계산·검증·변환 규칙 |
| 통합 | 여러 모듈이 연결되는 지점 (API 클라이언트, 서버 핸들러) | 응답 형식, 에러 코드, 규칙이 경계에서도 성립하는지 |
| E2E | 실제 브라우저에서 화면 흐름 | 화면 표시, 이탈 경고, 상태 전이, 네트워크 연결 |

어려운 로직이 어느 층에 모여 있는지에 따라 무게중심을 조정한다.

## 절차

### 1. 무엇을 확인할지 정한다

- 작업 이슈가 있으면 그 "작업 범위", "검증 계획", "원인"에서 출발한다. (`gh issue view <번호>`)
- 없으면 다음 세 가지를 한 줄씩 적는다.
  - **해결 확인**: 원래 문제가 사라졌음을 무엇으로 보일까
  - **회귀 확인**: 영향을 받을 수 있는 다른 동작은 무엇일까
  - **비용 확인**: 새로 생긴 복잡도, 의존성, 깨지기 쉬운 테스트가 있을까

### 2. 변경 위치로 층을 고른다

| 바뀐 곳 | 반드시 | 필요하면 |
| --- | --- | --- |
| 순수 함수·도메인 로직 | 단위 테스트 (경계값) | 같은 규칙을 쓰는 통합 테스트 |
| API 핸들러·모킹 서버 | 통합 테스트 | 해당 화면 E2E |
| API 클라이언트·데이터 훅 | 통합 테스트 또는 E2E | 에러 메시지 화면 확인 |
| 화면·폼·라우팅 | E2E | 규칙 위반을 서버가 다시 막는지 통합 테스트 |
| 진입점·설정·서비스 워커 | E2E (새로고침 포함) | `build` + `preview` |

### 3. 먼저 실패를 재현한다

버그 수정이라면 **고치기 전에 실패하는 테스트나 재현 절차를 먼저 만든다.**

- 단위·통합으로 재현할 수 있으면 실패하는 테스트를 먼저 쓴다. 수정 후 통과하는지 본다.
- 브라우저에서만 재현되면 재현 절차(URL, 클릭 순서, 기대·실제 결과)를 적고, 수정 전후를 비교한다.
- 재현하지 못했다면 "재현 못 함"이라고 적는다. 재현 없이 고친 것을 해결됐다고 보고하지 않는다.

### 4. 경계값을 고른다

해당하는 것을 고른다.

- **시간 의존 로직이 있는 경우**: 시작·종료 경계(정각, 1ms 전, 1ms 뒤), 자정 경계, 시간대 변환
- **목록·페이지 경계**: 동률 정렬, 페이지 끝에 걸친 항목 (중복·누락 없는지)
- **입력 경계**: 글자 수 최대값 ±1, 이모지(grapheme), 앞뒤 공백, 빈 값, 잘못된 형식
- **상태 전이**: 특정 상태에서 허용/거부되는 동작의 경계

### 5. 시간 의존 로직은 시계를 제어한다

시간에 따라 동작이 달라지는 로직이 있는 경우:

- **단위·통합**: 테스트용 고정 시각 유틸을 만들어 `new Date()` 대신 쓴다. 테스트 안에서 `new Date()`로 "지금"을 만들지 않는다.
- **E2E**: 브라우저 시계를 Playwright의 `page.clock`으로 제어하거나, 프로젝트에 QA용 시계 패널이 있으면 그것을 쓴다.

### 6. 실행한다

순서대로 실행하고, 앞 단계가 실패하면 멈추고 원인부터 본다.

```bash
npm run typecheck
npm test
npm run build        # 설정·진입점·의존성을 건드렸을 때
```

E2E가 필요하면 개발 서버(`npm run dev`)에 Playwright MCP로 접속해 확인한다. 스크린샷이나 스냅샷으로 근거를 남긴다.

### 7. 해결 이후를 점검한다

- **테스트가 구현이 아닌 동작을 검사하는가**: 내부 함수 이름이나 호출 횟수에 묶인 테스트는 리팩터링 때 거짓 실패를 만든다.
- **규칙이 한 곳에만 있는가**: 같은 규칙을 여러 곳에 따로 구현하지 않았는지 본다.
- **문서가 따라왔는가**: 가정이나 API 응답이 바뀌었다면 README를 갱신했는지 본다.
- **새 의존성·설정이 늘었는가**: 늘었다면 그 비용이 브리프에서 합의한 범위인지 본다.

## 보고: PR 본문에 남긴다

검증 결과는 채팅이 아니라 **PR 본문의 "검증 결과" 섹션**에 쓴다. (`pr-workflow` 스킬의 PR 본문 형식)

```markdown
## 검증 결과

### 이슈 대조
| 이슈에서 정한 것 | 실제 결과 | 근거 |
| --- | --- | --- |
| (작업 범위 항목 1) | 완료 / 일부 / 안 함 | (커밋, 파일 링크) |
| (검증 계획 항목 1) | 통과 / 실패 | (테스트 이름 또는 재현 절차) |

### 실행 결과
typecheck ✓ · test N개 통과 · build ✓

### 확인하지 못한 것
(이유와 함께. 없으면 "없음")

### 이후 비용·위험
(새 복잡도, 의존성, 깨지기 쉬운 부분)
```

- 실패한 항목이 있으면 숨기지 않는다.
- 이슈와 다르게 한 부분이 있으면 그 이유와 확정받은 댓글 링크를 단다.

## 도입 판단 기준 (React 프론트엔드 기준)

| 방법 | 판단 | 이유 |
| --- | --- | --- |
| 컴포넌트 테스트 (RTL + jsdom) | 보류 | 주요 위험이 로직(단위·통합)에 있고, 화면 위험은 E2E가 더 잘 잡는다. jsdom은 레이아웃·포커스·서비스 워커를 재현하지 못한다 |
| Vitest Browser Mode | 보류 | 실제 브라우저라 정확하지만 의존성·설정이 늘어난다. 컴포넌트 테스트가 필요해지면 jsdom보다 이쪽을 먼저 검토한다 |
| 속성 기반 테스트 (fast-check) | 선택 | 정렬·페이지네이션의 불변식, 상태 전이 방향 같은 속성 검사에 잘 맞는다. 해당 로직을 크게 바꿀 때 제안한다 |
| 스냅샷 테스트 | 쓰지 않음 | 의도가 드러나지 않고, 작은 마크업 변경에도 깨진다 |
